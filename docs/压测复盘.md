## 问题一：订单号碰撞被误判为幂等冲突

### 现象
场景一 5000 请求出现 **2 × HTTP 409**（0.04%），其余 4998 × 200。

### 诊断过程
1. 两条 WARN 日志均为：`命中 uk_idempotent_key 唯一索引，返回已存在订单：idempotencyKey=<uuid>`。
2. 但该 UUID 在 `t_order` 中**并不存在重复**（U-load 订单 5099 条、不同幂等键 5099 个）。
3. 统计同一秒内订单数高达 **165~170**。

→ 推断：冲突**并非** `uk_idempotent_key`，而是 **`uk_order_no`（订单号碰撞）**；代码把 `DuplicateKeyException` 一律当作幂等键冲突，于是释放了库存并调 `resolveExisting(幂等键)` 查不到订单 → 误返回 409「重复请求正在处理中」。

**根因**
- 原 `OrderNoGenerator` = `yyyyMMddHHmmss`（秒）+ 6 位随机数。同一秒 ~170 单时，6 位随机空间（10^6）的生日碰撞概率约 **1.4%/秒**，33 秒内出现碰撞是大概率。
- `catch (DuplicateKeyException)` 未区分具体唯一约束。

### Review 判断（关键上下文）

> **强烈建议选 A（增强订单号 + 区分约束）。**
> 仅改订单号（B 方案）是治标不治本。`DuplicateKeyException` 是一个宽泛的异常，只要发生唯一键冲突就会抛出……如果未来引入其他唯一约束，或在极端峰值下，代码依然会错误地执行"查幂等键 → 查不到 → 抛 409"的逻辑。
> 区分约束（A 方案）是治本。系统必须能正确识别失败原因，这是健壮性的底线。

> **落地建议**：
> 1. 订单号生成器：推荐改为 `yyyyMMddHHmmssSSS`（毫秒级）+ `AtomicLong`（3 位循环序列），或 Snowflake。
> 2. 异常区分逻辑：在 `catch (DuplicateKeyException e)` 中不要盲目相信它一定是幂等键冲突；**主动查一次数据库**——按 `idempotency_key` 查到订单 = 幂等冲突 → 返回原订单；没查到 = 订单号碰撞 → 生成新订单号重试（最多 3 次）。用 `e.getMessage()` 解析约束名依赖底层驱动，不够稳妥。

### 最终修复
- `OrderNoGenerator`：`yyyyMMddHHmmssSSS`（17 位毫秒）+ `AtomicLong` 3 位循环序列（共 20 位），单机每毫秒最多 1000 个不重复。加注释说明回绕边界。
- `OrderCreationService.create(request, idempotencyKey, orderNo)`：订单号由**编排层传入**，便于换号重试。
- `OrderApplicationService.createOrder`：
  1. 幂等抢占 → 预检命中直接返回；
  2. `stockService.reserve`；
  3. 循环 ≤3 次生成 orderNo 调 `create`：
     - 成功 → 回写缓存返回；
     - 捕获 `DuplicateKeyException` → **主动 `selectByIdempotentKey`**：命中 = 幂等冲突（回补多余预扣、返回首单）；未命中 = 订单号碰撞（换号重试）。

### 结果
场景一复测：**5000 × 200，0 错误**；`P1001=95000`、5000 单/5000 唯一幂等键、无负库存、应用 0 WARN。

### 复盘价值
★★★ 「如何区分 `DuplicateKeyException` 的唯一约束」「高并发唯一 ID 生成策略」都是高频面试题。

## 问题二：事务边界与重试的冲突

### Review 的关键警告（关键上下文）

> **如果 `createOrder` 方法上带有 `@Transactional` 注解**：当 `orderMapper.insert` 抛出 `DuplicateKeyException` 时，当前事务已被 Spring 标记为 rollback-only。虽然你 catch 住了异常，但如果在同一个事务中继续执行 `selectByIdempotentKey` 和重试 insert，最终外层提交时，Spring 会抛出 `UnexpectedRollbackException`，导致重试虽然执行了，但数据无法落库。
>
> 解决方案建议：
> - 方案一（推荐）：把 insert 抽到独立方法，标注 `@Transactional(propagation = REQUIRES_NEW)`，每次重试在新事务中。
> - 方案二：手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(false)`（不推荐）。
>
> 请务必根据当前项目的事务传播机制，选择最稳妥的方式。

### 核实与结论
只读核实当前代码：
- `OrderApplicationService.createOrder` **没有 `@Transactional`**（类注释明确「本类不做事务；落单事务在 OrderCreationService」）——纯编排层。
- `OrderCreationService.create` 才是 `@Transactional`。

因此重试链路**天然安全**，无需 `REQUIRES_NEW`、无需 `setRollbackOnly(false)`：
1. `create` 抛 `DuplicateKeyException` → 内层事务被标记 rollback-only 并回滚，异常向上抛；
2. 外层 `createOrder` 不在事务中，catch 后 `selectByIdempotentKey` 走**新的自动提交连接**，读到已提交数据；
3. 换号重试再调 `create` → **全新事务**。

> Review 判断成立的前提是 `createOrder` 带事务；本项目刻意把「编排（非事务）」与「落单（独立事务）」拆开（D4/D5 设计），从架构上规避了该陷阱。

### 复盘价值
★★★ 「事务传播 / rollback-only / `UnexpectedRollbackException`」经典面试题；同时体现「编排层与事务层分离」的设计收益。

## 问题三：性能瓶颈与 Little's Law

### 基线数据（修复 Bug 前）
- Hikari `maximum-pool-size` = 10。
- 场景一：**QPS 150.6/s**，P50 649ms / P90 724ms / P95 741ms / **P99 907ms**，Avg 642ms，Max 7424ms。
- 队列特征明显：100 并发争 10 个连接，平均等待与 Avg 642ms 高度吻合。

### Review 的调优指导（关键上下文）

> **先修 Bug，再调优复测。** 带着 Bug 调优，QPS 越高订单号碰撞概率越大，海量 409 会淹没真实瓶颈。
> 修完后把 Hikari `maximum-pool-size` 从 10 调到 20 或 30；Tomcat 线程默认 200 够用，暂时不用动。
> 同时建议把 `connection-timeout`（默认 30s）降到 3000ms，连接池彻底打满时快速失败、保护系统。
> 复测前务必 FLUSHDB 和复位 P1001 库存，保证基线一致；对比表格注明"单机压测，JMeter 与 App 共享 CPU 资源"。

（实现时 `connection-timeout` 已为 3000ms，无需改动；Tomcat 线程未动。）

### 调优后复测
- 修复订单号 bug + Hikari 10 → 30。
- 场景一：**5000 × 200，0 错误**；QPS 155.8/s，P50 626ms / P90 675ms / P95 692ms / **P99 809ms**，Avg 626ms，Max 1017ms。

| 指标 | 基线 | 修复 + Hikari 30 |
| --- | --- | --- |
| 成功 / 错误 | 4998×200 / 2×409 | **5000×200 / 0** |
| QPS | 150.6 /s | 155.8 /s |
| P50 / P90 / P95 / P99 | 649 / 724 / 741 / 907 ms | 626 / 675 / 692 / 809 ms |
| Avg / Max | 642 / 7424 ms | 626 / 1017 ms |

### 结论
- **QPS ≈ 并发 / 平均延迟**（Little's Law）。100 并发、Avg 626ms → 理论吞吐约 160/s，与实测吻合。
- Hikari 扩池主要改善**尾延迟**（P99 907→809ms，−11%），QPS 未显著提升 → 瓶颈更可能在**单机 CPU 与端到端 SQL 往返**：
  - 单请求落单事务含 `insert` + 2 次状态 `UPDATE` + 库存 `UPDATE` + outbox `insert`（约 5 次 SQL 往返）；
  - 幂等 `SETNX` + 库存 Lua 两次 Redis 往返；
  - 消费者/对账/超时等后台任务与 JMeter 同机争 CPU。
- 后续调优方向：减少状态 `UPDATE`、合批/异步化、进一步定位 CPU/慢查询。

### 复盘价值
★★★ 「压测 → 定位 → 调优 → 复测」方法论；连接池大小与吞吐/延迟的关系。

## 复盘（面试口径汇总）

| 主题 | 一句话口径 |
| --- | --- |
| 区分唯一约束冲突 | `DuplicateKeyException` 是宽泛异常，不能假设是幂等键；**主动查库**判断（查到幂等单=幂等冲突返回首单；查不到=订单号碰撞换号重试），不解析驱动异常消息。 |
| 高并发唯一 ID | 秒级时间戳+随机数在 ~170/秒即出现生日碰撞；改毫秒时间戳 + 本地 `AtomicLong` 序列（单机每毫秒千级）；多实例/更高性能用 Snowflake。 |
| 事务传播 / rollback-only | `@Transactional` 内 catch 唯一键异常后继续操作会使事务 rollback-only，提交时 `UnexpectedRollbackException`；应把易失败操作独立到新事务，或让重试发生在非事务的编排层。 |
| 连接池与吞吐 | 100 并发对 10 连接会排队（Avg 642ms）；扩到 30 改善尾延迟；`QPS ≈ 并发/平均延迟`，吞吐瓶颈需从 CPU、SQL 往返、锁与后台任务定位。 |
| 压测方法 | 先冒烟（1 线程 1 循环）→ 极限压测（无思考时间）→ 记录 QPS/分位/错误分布 → 修复→调优→复测；单机压测需注明客户端与服务端共享资源。 |
